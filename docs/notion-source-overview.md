
> ## 💡 소개  
>   
> **팀 전체 생산성을 위해 항상 고민하는 백엔드 개발자 이희망입니다.**  
>   
> 저는 "왜 이 방법이어야 하는가"를 설명할 수 있는 코드를 지향합니다. 기능을 동작하게 만드는 것을 넘어, 같은 문제라도 여러 방식으로 구현하고 비교해 본 뒤 **트레이드오프를 근거로 선택하는 과정**을 중요하게 생각합니다. 예를 들어 메시지 처리 방식을 정할 때 Spring Event·Redis·Kafka를 직접 구현하고 벤치마크로 비교한 뒤, "속도는 다소 양보하더라도 내구성과 확장성이 필요한 핵심 이벤트에는 Kafka"라는 식으로 판단의 이유를 남깁니다. 정답을 외워서 쓰기보다, 상황에 맞는 도구를 고르는 연습을 반복해 왔습니다.  
>   
> ## 핵심 역량  
>   
> **동시성 제어와 부하 처리.** 트래픽이 한 지점에 몰리는 상황(선착순 쿠폰, AI 채점 요청 폭주)에서 데이터 정합성을 지키면서 처리량을 확보하는 문제를 다뤄 왔습니다. DB 락 병목을 Redis Lua Script와 큐 기반 비동기 처리로 분리하고, 동기 호출의 스레드 고갈 문제를 메시지 큐로 풀어내는 등, "왜 이 구조가 필요한가"부터 설계했습니다.  
>   
> **외부 API 의존성의 신뢰성 설계.** 외부 시스템에 의존하는 백엔드가 마주하는 현실적인 문제 — 호출 제한, 장애 전파, 토큰 만료 — 에 대응하는 경험을 쌓았습니다. Rate Limiter로 호출을 통제하고, Fallback과 Circuit Breaker로 단일 장애점을 제거하며, 종료 시점의 데이터 손실까지 막는 식으로 "흔들려도 버티는" 시스템을 고민합니다.  
>   
> **메시징과 이벤트 기반 아키텍처.** Kafka와 Redis Streams를 활용한 비동기 처리, DLT 재시도와 Outbox 패턴을 통한 메시지 유실 방지, Consumer Group 기반 수평 확장 등 이벤트 기반 설계를 실무와 프로젝트에서 다뤘습니다.  
>   
> 검증은 추측이 아니라 데이터로 합니다. 부하 테스트(K6)와 벤치마크, 단위 테스트로 "구현했다"가 아니라 "이렇게 동작한다"를 확인하는 습관을 들였습니다.  
>   
> ## 관심 분야  
>   
> 요즘은 **분산 환경에서의 정합성과 메시징**에 가장 관심이 많습니다. 여러 서버·여러 소비자가 같은 데이터를 다룰 때 순서와 정합성을 어떻게 보장하는지, 장애가 났을 때 어떻게 복구하는지가 백엔드의 본질적인 어려움이라고 생각합니다.  
>   
> 또한 **AI를 협업 도구로 활용하는 개발 워크플로우**에도 관심이 있습니다. 제약사항과 검수 기준을 명확히 정의해 AI 에이전트(Claude Code)에게 구현을 맡기고, 결과를 직접 리뷰·검증하는 방식으로 생산성을 높이는 시도를 해 왔습니다. 다만 AI는 어디까지나 도구이고, 설계 판단과 검증의 책임은 개발자에게 있다고 생각합니다.


프로젝트를 통해, 위에서 말한 역량을 **구체적인 문제 해결 과정**으로 보여드립니다. 각 트러블슈팅은 "어떻게 문제를 발견했고, 왜 이 해결책을 골랐으며, 결과가 어땠는지"의 흐름으로 정리했습니다.

- **CS25** — AI 기반 CS 학습 플랫폼 (100명+ 사용자). AI 피드백 파이프라인의 비동기 처리(BlockingQueue→Redis Streams), 워커 오토스케일링, 외부 AI API 장애 대응(Fallback·Circuit Breaker)을 다룹니다.
- **이커머스 서버 (항해99)** — 선착순 쿠폰 동시성 제어, 메시징 3종 비교 후 Kafka 선택, N+1 쿼리 최적화 등 동시성·메시징·쿼리 최적화를 직접 비교하며 구현했습니다.
- **AI Trade Server (MonestAI 인턴)** — 증권사 Open API 연동의 안정성·정확성 설계. Rate Limiter, 외부 API 신뢰성 설계, 실시간 데이터 배치 저장을 다룹니다. (실무 프로젝트로 코드는 비공개이며, 설계 의도 중심으로 정리했습니다.)
